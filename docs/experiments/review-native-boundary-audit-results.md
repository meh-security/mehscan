## Concrete fifteen-claim package

The profile-image seed touches original buckets of sizes one, three and eleven.
The six-claim workspace selection empties the first two. Nine members of the
eleven-claim bucket remain native. Include all fifteen in the next comparison so
the affected package measures the same one-unit reduction as the population
projection: **three native packets versus two hybrid packets**, rather than
claiming a two-unit saving from a selected-only six-claim slice.

| Hybrid placement | Claims and deciding work |
| --- | --- |
| Workspace, shared handler evidence | `profileImageUrlUpload`: URL-to-fetch relationship, two cookie-authenticated state writes, and the fixed redirect. Keep four separate dispositions and their actual properties |
| Same workspace packet, independent peers | Fixed redirects in `profileImageFileUpload` and `updateUserProfile`. They share bounded redirect/configuration evidence but keep their own handler and caller conditions |
| Native packet, nine retained peers | TOTP storage; basket-item duplicate-key mutation; profile username cookie-authenticated write; chat coupon operation; basket resource access; current-user response field; generated-resource mass assignment; order resource access; data-erasure cookie-authenticated write |

This is explicit `packet_batch` placement, not an assertion that six claims share
one authorization policy. In particular, the two URL-handler state claims ask
about cookie-authenticated state changes. An authenticated owner selector does
not settle their CSRF property. AL's owner-selector negatives cannot be reused
as their verdicts.

The bounded source includes the complete three small handlers, server imports and
relevant configuration/registration ranges, cookie parsing and URL-encoded body
parsing, the token-map helper, cookie writer, upload configuration, `BASE_PATH`
initialization and custom `asyncHandler`. The native peers also retain their
ordinary source/sweep evidence and lookup API. The eight explicit windows do not
certify every global middleware, credential issuer or deployment condition.

Source observations that shape the future proof requirements:

- The URL handler passes request `imageUrl` to `fetch` after a cookie-token map
  lookup. Its challenge regex sets a flag; it is not an allowlist. Any finding
  still needs its accepted-caller, input and network-effect conditions.
- Both normal and error-fallback paths can update the profile image. Preserve
  the separate selected writes and qualify browser cookie delivery, request
  construction and effective origin/request-token controls where unestablished.
  No live browser or deployment behavior was tested.
- All three redirect expressions use configured `BASE_PATH` plus `/profile`.
  Review request influence and retain the trusted-configuration scope; do not
  transfer a blanket handler-safety conclusion from the redirect property.
- Profile-image routes are registered before the later JWT challenge middleware.
  Route order and handler cookie checks must be read as supplied; a later global
  check must not be assumed to protect an earlier registration.

These are implementation-agent source observations for experiment design, not
independent gold labels or new classified findings.

   supported mechanisms, severity conditions and useful unresolved leads. Trace
   deciding lookup questions, returned evidence and subsequent decisions. Measure
   actual input/output, calls, model time and complete-package time. Input volume
   alone remains neither success nor failure.

   proof while removing substantive reconstruction or improving complete-package
   time. If only the co-located peers regress, correct or remove that placement;
   retain the useful URL-handler shared investigation. If native already shares
