# BG: full Juice hybrid comparison

Both corrected selective hybrids review the same 116 Juice Shop claims as the
stored native packages. The main question is quality at a comparable complete
package price. Native remains the default for local work; the eight selected
handler/cookie relationships share one workspace. This is a development
comparison on familiar source, not independent accuracy measurement.

**Both hybrids complete 116/116 claims. Neither demonstrates a whole-app price
reduction.** Terra hybrid is at practical price parity with stored native Terra.
Sol hybrid's known price is already higher than stored native Sol, before one
unmeasured timeout. Useful workspace state survives, while the source audit finds
material qualifications and gaps in every option. Keep the useful pieces and
correct the deciding facts; do not promote or discard an entire workflow.

The [frozen plan](review-full-hybrid-comparison-plan.md) and
[explicit recovery record](review-full-hybrid-sol-retry.md) retain the execution
and comparison boundaries. The study is closed; no further paid run follows.

## Quality findings that change the interpretation

### Shared cookie work is useful, but closure still differs

Both full workspace packages retain the server-side image fetch and three scoped
fixed-redirect negatives. Terra reports four CSRF mechanisms with browser cookie
delivery and site/deployment qualifications; Sol retains the same mechanisms as
four actionable uncertainties. Privacy-request creation is not account deletion.
Neither package establishes an attacker origin or deployed browser delivery.
The same contrast appeared in the earlier focused BF retest.

The shared question and propositions are retained once with separate consumers.
That demonstrates useful state and review-package fidelity. It does not show
that a missing memory subsystem caused the remaining difference, or that every
conditional source mechanism needs exhaustive deployment investigation.

### Exact dependency contracts matter more than helper names

The export directly declares `jsonwebtoken` 0.4.0. Its signing implementation
uses `expiresInMinutes`; the application's `expiresIn: '6h'` does not establish
six-hour expiry under that binding. Stored Sol native's three expired-token
findings overstate that issuance detail. The cache still lacks fresh validation,
but that is distinct from demonstrating expiry of tokens issued by this code.
Sol hybrid's credential-authenticity uncertainties are not automatically lost
supported findings. However, its separate generic cache unit still asserts the
six-hour premise. Its framework unit recognizes material legacy-verifier
uncertainty while the cache unit assumes a stronger contract. These are
conflicting assumptions across units; they do not prove the model had already
learned the exact expiry-option behavior and forgot it.

There are two JWT bindings: `express-jwt` 0.1.3 declares its own
`jsonwebtoken ~0.1.0`, while application helpers directly import 0.4.0. Both
inspected verifiers delegate to compatible `jws` without rejecting an empty
signature first. The inspected `jws`/`jwa` chain selects the header algorithm and
accepts an empty signature for `none`. This makes a random-secret `denyAll`
name insufficient proof of rejection under the normal declared binding.
Sol hybrid preserves this question on the exact protected routes. Check each
caller's independent gates: quantity has accounting/IP middleware, and 2FA
disable has a password comparison against cached data. Do not transfer a bypass
or a safe conclusion indiscriminately between them.

These are evaluator-only static primary-source checks. Installed dependencies
and deployed behavior were not attested. Sources: [express-jwt 0.1.3](https://raw.githubusercontent.com/auth0/express-jwt/v0.1.3/lib/index.js),
[nested JWT 0.1.0](https://registry.npmjs.org/jsonwebtoken/-/jsonwebtoken-0.1.0.tgz),
[direct JWT 0.4.0](https://registry.npmjs.org/jsonwebtoken/-/jsonwebtoken-0.4.0.tgz),
[jws 0.2.6](https://registry.npmjs.org/jws/-/jws-0.2.6.tgz),
[jwa 0.0.1](https://registry.npmjs.org/jwa/-/jwa-0.0.1.tgz).

### A single-record update does not prove the same record was checked

Four like-review scanner branches describe one check-to-effect relationship.
MarsDB 0.6.11 defaults updates to one record **sorted by `_id`**, while `findOne`
has no default sort. Its `_id.$in` fast path preserves supplied ID order. With
existing IDs A < B, `$in: [B, A]` can check B but update A. A user who already
liked A but not B can therefore pass the earlier likedBy check on B while the
increment selects A. This is a concrete version-bound mismatch, not merely the
observation that an object selector is accepted. It also differs from the
separate non-atomic/concurrent-like lead.

Stored Sol native's confident four dismissals are questionable on that deciding
relationship, and new Sol repeats those dismissals. Terra's retained uncertainty
is useful. The evaluator's first
single-update observation was insufficient; checking selection order changed
the conclusion. The normal declared binding and suitable existing records are
conditions, and no application/dependency code was executed.
[MarsDB 0.6.11 source](https://registry.npmjs.org/marsdb/-/marsdb-0.6.11.tgz)
also confirms compilation of string `$where` predicates. The two query routes
retain their challenge/configuration conditions. Do not upgrade that into an
unconditional deployed host-code-execution claim, or retroactively pretend the
model inspected the vendor source.

### Same issue labels can preserve different mechanisms

Terra native's broad generated-CRUD finding identifies privileged registration;
Terra hybrid's finding at that same review ID identifies the basket-item owner
gap, already represented elsewhere. Hybrid retains role assignment as a separate
uncertainty, but does not close its authority consumer. That is a real package
tradeoff hidden by an unchanged `issue` label.

Sol native uses that broad ID for the basket-item gap; Sol hybrid instead
identifies unauthenticated generated Product PUT. The commented-out guard and
declared Finale update controller support that different mechanism. Sol also
retains the separate registration-role finding. Compare these mechanism unions
instead of treating all four `issue` labels as the same result.

The inspected Finale 1.2.2 create controller copies request fields before
`model.create`. `excludeAttributes` strips output after creation;
`readOnlyAttributes` is the separate input control and is not configured here.
The model accepts privileged roles, login signs the persisted role, and role
middleware consumes it. These facts support the registration mechanism with
the version-binding qualification. They also support the registration rejection
fallthrough: sending a 400 and then calling `next()` does not itself prevent
creation, and a later second-response error does not undo the earlier write.
The User model lacks the claimed nonempty constraints.
[Finale 1.2.2 source](https://registry.npmjs.org/finale-rest/-/finale-rest-1.2.2.tgz)
was inspected only by the evaluator.

### Caller depth must answer the selected question

The three Windows file-handler claims need preceding `serve-index` behavior.
Ordinary dot-dot traversal can fail its root check, but that alone does not
settle the handler. On Windows, rooted/drive-qualified backslash values can
have different `path.join` and `path.resolve` destinations: the index can see an
absent contained path and continue while the custom handler resolves outside
its root. The custom guard rejects only forward slashes. Preserve runtime,
reachability and filesystem conditions; neither an omitted slash check nor the
existence of index containment alone is decisive.
[serve-index 1.9.1](https://raw.githubusercontent.com/expressjs/serve-index/v1.9.1/index.js)
and pure `node:path.win32` calculations establish this evaluator interpretation.
No target requests, filesystem accesses through the application or target code
execution were used.

New Sol closes these three former uncertainties as issues, but its concrete
dot-dot examples still omit the preceding index behavior. The conditional
containment mechanism is useful; those particular reachability examples need
correction. A source audit must retain both observations.

Conversely, the source-generated snippet-key map is a useful local invariant:
absent keys return before the filesystem read. Repository-key provenance is
sufficient for this scoped closure without inventing a mandatory investigation
of every hypothetical arbitrary-source-write chain. Country-mapping output has
available configuration/schema source; leaving representation uninspected is
avoidable work, distinct from an unavailable external policy.

### Filename safety does not prove YAML integrity

The same metadata has a different deciding question for deserialization.
`/file-upload` registers a ZIP handler that, when file-write challenges are
enabled, can overwrite a valid metadata file while remaining within the working
directory. Existing-key/basename gates continue to pass. js-yaml 3.14.1's
[full schema](https://raw.githubusercontent.com/nodeca/js-yaml/3.14.1/lib/js-yaml/schema/default_full.js)
constructs [JavaScript functions](https://raw.githubusercontent.com/nodeca/js-yaml/3.14.1/lib/js-yaml/type/js/function.js).
The codefix and RSN consumers subsequently call `fixes.find(...)`, allowing a
YAML-provided method to be invoked under that static chain. RSN additionally
requires its later CLI invocation. No payload or application code was executed.

Both Sol packages dismiss these as local metadata with no lower-trust producer
established. The complete package already contains a concrete conditional write
mechanism, so that trust premise needs correction or explicit uncertainty.
Terra preserves the consequential question. Do not transfer this function-call
effect to the lint/schema or snippet-hint consumers automatically: their effects
differ. The earlier traversal negatives remain useful. This is why closure and
fact reuse must follow the rule's deciding relationship.

These differences buy or leave concrete reviewer work, rather than uniformly

### Impact, severity and adjacent leads stay separate

The packages retain the important mechanisms for duplicate-key basket selection,
cross-owner item update/checkout, prompt-only coupon limits, dynamic sensitive
response fields, HBS layout selection, plaintext TOTP storage and hardcoded

measure equivalent impact: coupon use requires a model invocation and valid
redemption; current-user JSONP exfiltration additionally requires cookie delivery;
layout output is truncated and path-dependent. The source supports bounded
mechanisms, not every stronger impact interpretation.

An owner-constrained card or deluxe-user selector does not certify payment
settlement. The unsupported-payment-mode path still reaches role/token issuance.
Adjacent source leads must remain visible even when they overlap a selected
finding. Fewer lead objects in one package need not mean lower coverage when
the same mechanism is a selected outcome; a genuinely different payment,
concurrency or credential chain must not disappear under deduplication.

Both Sol packages retain the unsupported-payment-mode lead. Terra native
retains it, while Terra hybrid drops it without another selected finding covering
that transition. That is lost useful reviewer work, even though the narrow
deluxe owner-selector verdict remains justified under an authentic-subject
premise. This native-peer variation is not a causal workspace-routing effect.

## Practical decision and stopping boundary

Keep native for local SQL/API/parser closure and the selective workspace for
prepared relationships with compatible caller scope. The full result does not
justify replacing all native work or discarding workspace state. Do not promote
one model or route from verdict totals or latency alone.

The next useful correction is access to the **specific versioned dependency
fact** that can change a verdict, with provenance and its unresolved applicability
kept in the existing state. JWT binding, MarsDB selection order and cookie defaults
are different deciding facts; a generic summary cache is not sufficient. Start
with saved/offline cases and the existing lookup interface, rather than another
whole-app run or broader grouping pass. Most price work must reach the native
continuations in the other 101 claims; optimizing the selected eight alone has
the limited ceiling measured above.

The second direction is mechanism-level package comparison and targeted follow-up.
Preserve supported mechanisms, local negatives and useful uncertainties across
review IDs; avoid replacing one unique finding with a duplicate at an unchanged
label. A dependency lookup should end when it settles the selected mechanism or
exposes a precise unavailable fact. Dig further only when the next fact can
change that result or a stated stronger impact question.

Freeze features and stop paid full-app repetition after this comparison. A new
small live slice needs a concrete corrected boundary, source parity and a
quality/price question not already answered by the saved receipts. Broaden again
only after that correction retains the representative mechanisms and controls
at a useful complete-package price. No automatic new app or native rerun follows.

Model-price equivalents exclude unmeasured human planning, source preparation,
controller compute and adjudication. Earlier failed/focused studies remain
separate sunk experimental spending, including their unknown charges. This
comparison cannot establish lower total production cost. Physical quote checks
and native source validation establish artifact fidelity, not semantic truth.
