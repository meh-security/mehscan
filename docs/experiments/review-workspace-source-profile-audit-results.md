## What failed, and the surgical correction

The original proposal requests eight source windows/12,168 canonical bytes. Sent
through the ordinary application-context hook, only four additions materialize:
app registration, authentication middleware, default-accountability helper and
the file-service constructor. The resulting six-window packet, including the
two native route snippets, contains **4,488 bytes**. Both arms agree exactly.

Four requested windows are nevertheless missing:

- Accepted-token accountability producer.
- File deletion override and physical storage effect.
- Parent service construction/accountability binding.
- Parent single/query/bulk deletion and permission/effect ordering.

This is a red flag because a parity receipt establishes agreement between arms,
not delivery of the intended intervention. Workspace's separate eight-window
evidence API does not make the ordinary four-window path equivalent. The earlier
proposal stays unchanged and unapplied as a complete eight-window intervention.

`review_workspace_pilot.py` now supports an explicit optional
`required_initial_source` map keyed by the comparison's native bundle/claim key.
Each required window carries its path, range and whole-file hash. Preparation
checks coverage of actual source lines independently of cross-arm equality and
rejects an omitted profile before provider preflight/inference. Adjacent supplied
windows can cover a requested range; conflicting text, stale hashes, invalid
coordinates and unknown bundle keys fail. The coverage receipt is hash-bound to
the prepared run and checked when loading it. Existing designs remain supported.
This is an experiment-readiness guard, not a security proof or a new selector.

## Source acquisition without a second security review

The alternative profile reuses the authentication middleware actually returned
to AD native. Its other source is acquired with three typed queries:

1. The exact app continuation already requested in AD's rejected native batch:
   request 301–480, actual returned source `api/src/app.ts:301–434`.
2. The exact accepted-token producer request from that same batch:
   request 1–400, actual `api/src/utils/get-accountability-for-token.ts:1–88`.
3. The default-accountability declaration named by the returned middleware import
   and located in AD's returned path index: actual body at
   `api/src/permissions/utils/create-default-accountability.ts:3–13`.

The third logical query uses native symbol lookup plus a source read. Total:
**three queries, four units, four native commands, 9,279 received native JSON bytes,
169 ms**, no model. Whole-file hashes match AD before and after acquisition.
Returned ranges are retained, including EOF clipping; no new security-specific
range cuts, verdict, interpretation, question state or applicability assertion is
imported. The profile caption is neutral, and provenance remains outside the
reviewer packet. The source-import/path check is a locator, not authorization.

This is assisted selection from prior deciding requests. It shows that the next
reads were already identified and cheap to retrieve; it does not demonstrate an
automatic selector for unseen operations. AD's sixteen calls and prior audit/model
work remain spent. Choosing a caller-only intervention is still an operator choice.

## Remaining work and decision

The caller control supplies initialization and registration source missing from
AD workspace, but does **not** complete even the caller-module binding: the app's
`authenticate` import at `api/src/app.ts:71` lies outside the returned continuation.
AD native had read it in 1–300; that does not make it present in this fresh packet.
A matching name and filename are insufficient import evidence. The original
eight-window proposal also omits that import. Retain the already-returned source
when building the next explicit profile instead of asking another model to find it.

The caller control also omits the previously inspected service and permission
bodies. The original-key/post-hook-key/storage qualification and
deployed hook/flow uncertainty therefore remain material. A model must still
inspect the selected effects and their guards; authentication source cannot close
the resource authorization claims by itself. No model behavior is tested here.

The practical next implementation is a **common explicit source-profile channel**
for ordinary and workspace preparation, with the same source-hash/scope binding,
requested-coverage gate and limits. Use it to compare the intended eight windows
honestly, rather than silently truncate them or permanently shrink the workflow
to fit four. Keep native policy-lead defaults separate from explicit prepared
source. This is narrower than a generic memory subsystem or new AI grouping pass.

Then measure how profiles are selected: already-returned source and named deciding
requests can be acquired without another model conversation, but unseen operation
selection remains unproven. Log selection/acquisition work and stop if it requires
another full security investigation per claim. Only choose a small diverse paid
package after source delivery and selection costs are reviewable. An unchanged AD
retry, bigger review budgets and a full-app rerun are not the next step.
