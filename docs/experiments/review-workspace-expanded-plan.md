## Question and arms

Which package produces supported mechanisms, correct local closures and useful
uncertainty with less repeated investigation and acceptable review time?

| Arm | Work formation | Initial evidence | Seed notebook |
| --- | --- | --- | --- |
| A (`control`) | Singletons | Native windows and bounded route references | No |
| B (`treatment`) | Singletons | Bounded complete local operation/effect regions | No |
| C (`complete_groups`) | Rule-aware investigations | Same complete regions, shared within a group | No |
| D (`complete_memory`) | Singletons | Same complete regions | Original wallet notebook only on routes that call its helper |

A versus B tests source preparation. B versus C tests concrete context sharing.
B versus D retests consumption of a scoped fact when a different missing local
handler read no longer necessarily forces another model turn. The experiment is
not a full factorial study and does not isolate every aspect of the existing
workspace from the ordinary worker. The previous ordinary control is descriptive
reference data, not a newly matched arm.

## Source and state controls

The complete profiles include local module/handler bodies and the relevant
registration/policy/effect configuration regions. In particular, basket and the
generated-resource case receive the intervening factory/hook region missing from
the previous notebook trial. The sources are raw snapshot bytes; no known answer
or authorization conclusion is preloaded. Helper implementations can still
require a deciding lookup. "Complete" describes these bounded operation regions,
not compiler resolution of every dependency or certification of every caller.

Recipe ranges and source hashes are frozen in `source-recipes.json` and the
native bindings. Contained preparation snippets are removed from the focused
view without removing original provenance. Partial scopes remain explicit.
The notebook is unchanged, source-bound and untrusted reviewer interpretation;
it cannot transfer a wallet verdict to another resource. Selection uses the
selected registration's helper reference, not an expected verdict.

Working SQLite state and private provider conversations are independent per arm.
Two additional arms reuse the same immutable read-only native work/plan as A;
they have separate working state, source journals and private sessions. No arm
records or supersedes a native decision. Arms execute serially, avoiding
cross-arm model contention and shared native-controller lock contention.

## Allowance and failure accounting

This is a new, explicitly expanded experiment. Older closed allowances and
unknown costs remain in their original ledgers.

- Same `gpt-6.1-sol`, medium effort, CLI `0.164.0-alpha.11.1`, protocol v2 and
  category lookup API in every arm.
- Six model calls per work item, including grouped work; no multiplication by
  group size. Native per-claim research rounds are explicitly five in this
  experiment, allowing six calls. Ordinary defaults remain unchanged.
- At most 48 model calls per arm, 192 across four arms, with a 2,400-second arm
  execution ceiling and a 9,000-second absolute whole-comparison deadline.
- Twenty-four query units per investigation including its preparation locators;
  at most 200 query units and 4 MiB of source/result allowance per arm.
- Input/output safety ceilings are generous: 3M input and 100K output per arm.
  Actual totals and final-call threshold overspend are always reported. A 10%
  token increase does not disqualify a package that improves useful review.

Case errors and unresolved work retain paid usage and do not erase completed
claims. With known usage the runner can continue independent work items. Unknown
usage blocks further dispatch in that arm; independent arms retain their own
fixed allowances. No missing case is silently dropped, converted to a dismissal,
or counted as a successful closure. Final summaries enumerate all selected IDs.

## Evaluation

Judge each mechanism and its conditions from actual inspected source, not old
verdict labels. Report separately:

1. Supported findings, unsupported findings and wrong dismissals.
2. Scoped local negatives versus retained adjacent mechanisms/leads.
3. Resolved relationships, precise remaining questions, unassessed claims and
   records awaiting reconsideration.
4. Model turns and elapsed time to useful disposition, source repeated across
   packets, lookup usefulness and inconsistent reconstruction of the same flow.
5. Actual input/output/cached tokens, preparation work, native queries, rejected
   turns and unknown counters.

Prefer an approach that preserves mechanisms and actionable uncertainty while
reducing reviewer reconstruction or completing more decisive relationships.
Extra input and modest output are acceptable for that benefit. Fewer scanner
claims, shorter prose, fewer native calls or native schema validation alone are
not quality evidence. Analyze by family as well as whole package so a hybrid
workflow can be supported rather than forcing one universal strategy.

No full-app rerun, claim filtering, automatic publication or richer CLI work is
part of this comparison. A grouping planner remains a separate question: this
matrix first tests deterministic groups where the shared investigation is known.

## Explicit controller repair after the unchanged first pass

The first pass exposed two controller/contract problems: narrower wording under
an existing deciding-question ID was rejected despite unchanged claim scope;
citations spanning two supplied helper definitions were rejected across a blank
separator. These are accounted as operational failures, not evidence that a
source or grouping approach produces worse security reasoning.

After all four original arms finish, a separately frozen controller-only phase
applies the same two fixes to eligible failures in every arm. It forks working
state into a separate directory with an explicit runtime-fork receipt, preserves
all earlier artifacts and paid costs, and retires earlier sessions. Before
replaying an unchanged paid answer without provider dispatch, it requires the
same deciding context beyond binding/budget and identical source-handle mappings.
Question continuations retain the original open question and record their own
requested wording. Citation projections use only supplied ranges and reject any
unseen substantive code. No previously settled claim is reopened.

Call, query, byte and token counters are conserved: six calls per investigation,
48 per arm and 192 overall still include paid rejected turns. Repair takes at
most 900 additional active seconds per arm; first-pass plus repair active time
stays below 2,400 seconds and the original 9,000-second whole-matrix deadline
still applies. The fork's 3,600-second wall ceiling accommodates waits between
serial arms while preserving original call timestamps; the stricter active-phase
clock remains enforced. Unknown usage still blocks further dispatch in that arm.

Report raw first-pass and amended results separately, including every repair
continuation and its latency. The first unused repair manifest was stopped while
waiting, before migration or dispatch; its script/package are archived. The
executing manifest is `repair-binding.json` version 2. This is an explicit
experiment migration, not a general runtime-binding bypass or product migration API.

Replay checks subsequently exposed global category-guidance leakage and local
question/proposition-name collisions across independent contexts. A second
isolated state correction scopes guidance and names, preserving the original
allowances. Changed deciding contexts require a fresh counted turn; equality
checks were not relaxed. A final offline-only proposition-name repair had zero
provider allowance. The results preserve the complete phase history, including
an explicitly recorded local migration abort before provider dispatch.
