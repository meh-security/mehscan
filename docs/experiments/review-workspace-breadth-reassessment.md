## Corrected experiments

### 1. Broaden work formation and fallback evaluation

Use six to eight real operations outside the twelve development cases. Include
the two newly discovered Juice Shop pairs, Directus multiline/inline callbacks,
a shared service called with compatible and incompatible policies, and an
unrelated local-closure case that should not trigger caller discovery. Freeze
source, IDs, callback/service spans and evaluator expectations before tuning.

Compare the existing deterministic proposal with a compact AI proposal on this
subset only. The AI pass receives bounded claim/operation metadata and a stated
grouping question; request targeted source when compatibility cannot be decided.
It must identify the deciding work shared, separate per-claim verdicts and mark
uncertain bindings. It may propose no group. A suggestion is not a verified fact.
Count its own model calls, input/output, lookups and time. Do not ask it to review
the application or close vulnerabilities during planning. Do not build a general
semantic-memory system for this diagnostic.

Source-adjudicate proposed relationships before live grouping. Report both
missed useful relationships and unsafe merges. Examine whether a small native
AST callback/registration extension or a bounded AI planner addresses actual
relationships more practically; do not assume either wins. Stop the AI variant
if its proposals require substantially repeating a full investigation to verify.

Explicitly distinguish **packet batching** from **shared investigation**. Several
local claims can be presented together without asserting common caller policy.
Where no shared investigation is established, compare retaining native batching
with singleton fallback. Do not turn the entire unsupported population into
separate conversations by default as an assumed efficiency improvement.

### 2. Run a broader live package comparison

Prepare approximately 24 real claims from at least two pinned applications,
outside the twelve-case workspace tuning slice, plus eight reserved claims for
confirmation after one targeted correction. Add a third corpus if the first two
cannot supply needed constructions. Require supported positives, clean controls,
precise unresolved cases, incompatible callers and both useful/low-affinity
sharing. The saved Juice Shop slice contains no safe parameterized SQL control;
do not call its two SQL positives a balanced SQL test. The inspected saved
Directus inventory has no SQL candidates either. Small synthetic SQL fixtures
can test protocol/semantics, but cannot substitute for real-corpus coverage.

Main comparison: the current supported native workflow with its **20-review
bundle default** versus the frozen experimental workspace package. The historical
singleton runs remain diagnostics; older unsupported dismissals are not accepted
quality baselines. Use the same capable model/effort, claim selection, source,
lookup availability and applicable category/API-contract policy. Retain every ID.
Label this as an end-to-end package comparison, not isolated proof of grouping,
memory or prompting. Document the treatment's unsupported-case fallback.

Budget fairness must be explicit before execution: a component with n selected
claims must not receive six calls in a group versus six per singleton and then
claim the cap difference as eliminated reasoning. Freeze comparable aggregate
investigation allowances, query/byte/time limits and concurrency. Verify how the
runner maps them to native bundles/work items. If the native workflow cannot
express equivalent task caps, retain a practical-default comparison separately
and mark cap-affected results as censored for causal efficiency claims. Do not
silently change native bundle size to one to make accounting convenient.

Run the first eight claims as a prespecified safety/feasibility wave, then the
remaining sixteen under the same frozen package. Do not tune between waves and
still call them one fixed-controller result. Pause paid expansion on a wrong
dismissal, unsafe applicability transfer, lost supported mechanism or unknown
usage. Preserve costs, diagnose the defect, and use a separately frozen affected
case/confirmation allowance after a correction. No silent paid repairs.

For each operation, assess mechanism, conditions, severity/actionability, remaining
deciding question and output status independently of the local native verdict.
Finding, scoped negative, unresolved mechanism and unvalidated lead are distinct.
An evaluator ledger can expose the product's operation-record gap without first
building that feature or promoting lead text into a finding. That known gap still
blocks a whole-package quality success claim when a required finding survives
only as a lead.

Measure actual input/cached input/output, model and wall time, preparation/planner
overhead, deciding turns, repeated source and duplicate investigation. Report
outcomes by application, rule/closure family, sharing opportunity, fallback and
cap status. Seek a repeatable operational benefit with supported mechanisms and
actionable uncertainty preserved. Token-percentage reductions are not gates.
Use targeted ablations only for a concrete ambiguity; do not start a full
factorial or model/effort sweep. Cases already used in earlier audits are held
out from workspace tuning only, not globally unseen security benchmarks.

## Investment decision

Continue the workspace as experimental infrastructure, but stop adding helper/
dependency/CLI features as a substitute for validation. The immediate question
is whether the workflow covers useful work beyond a few named-handler operations
and compares favorably with real native batching. Dependency contracts and
independent operation records remain important targeted quality work, not
prerequisites for answering that generalization question.

Proceed to a larger application slice only after the broader package and reserved
confirmation preserve quality and show useful benefits across more than one
favorable family. Narrow the supported scope if gains remain confined to local
SQL or duplicate native observations. If singleton fallback dominates and worsens
whole-package work, keep grouping as a selective optimization and retain native
batching elsewhere. This reassessment launches no paid run and reopens no closed
experiment allowance.
