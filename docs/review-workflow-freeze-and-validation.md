The actual native question asks whether the exact unauthorized action is rejected
before the protected effect, including inherited policy. This fits the proposed

The deciding question is whether the correct action/key/field checks survive
single, batch and query dispatch before their corresponding update/delete effects.

and query helpers delegate through `this.updateMany` / `this.deleteMany`.
`updateBatch` forks the concrete constructor with preserved accountability before
calling the single-item helper. These are concrete shared implementation facts,
not evidence that all callers have identical authorization or are safe.

Keep the subclass dispatch, inherited `validateAccess`, exact selected keys,

## Finite validation and stopping decision

1. **Keep implementation fixed.** Complete source/packet preparation for the
   four comments claims. Inspect the relevant inherited policy chain, actual
   native question and ordinary packet membership; capture equal supplied source
   in both paths with no reservations. Keep expected proof outside model input.
   If that graph cannot be bounded, report the specific obstacle and stop
   preparation rather than rewriting the protocol or calling everything unknown.
2. **At most one new-family comparison after readiness.** Proposed design: Sol
   medium native/workspace and Terra 6.1 medium native/workspace, serial and with
   counterbalanced engine order. One matched unit per arm, six calls/24 query
   units/512 KiB received JSON/900 seconds per unit: at most 24 reachable calls
   across four arms, not another per-candidate allowance. Use the frozen contract,
   addressed source and separate verdicts; configure the workspace bound explicitly.
   Freeze actual source/configuration/descriptors and allowances before paying.
   This proposal is not a runnable experiment or paid dispatch in AV.
3. **Evaluate the review package.** Compare the exact check-to-effect proofs,
   subclass dispatch, caller distinctions, supported scoped negatives and honest
   policy uncertainty, plus calls, lookup purposes/results, input/output, provider,
   controller/preparation time and assisted work. Label agreement, fewer queries
   and token reduction alone do not pass. Existing positive/unknown regression
   packages remain controls, not newly validated held-out mechanisms. This
   potentially clean family alone cannot establish balanced whole-app accuracy.
4. **Make one practical decision.** If native is equally useful and cheaper for
   this family, retain native here; keep workspace where its qualifications or
   partial closure help. If workspace preserves proofs and materially improves
   the package, keep that family-specific use without universalizing it. Mixed
   labels need source adjudication, not an automatic rerun. A wrong dismissal or
   lost supported mechanism calls for a bounded diagnosis and affected regression,
   not an immediate extra paid repair or wholesale discard.
5. **Stop the experiment series at that decision.** A further live test must name
   a new consequential uncertainty. Do not force consumer reopening, repeat raw
   citation arms, enlarge budgets to finish an old run or start a full-app review.
   Production/default promotion would need an independently adjudicated mixed
   validation package with complex positives, clean controls and genuinely missing
   facts, plus realistic source-selection/preparation cost. That is a separate
   deployment-readiness decision, not automatic continuation of this plan.

The known parameterized SQL control remains offline: the saved Juice inventory
has no admitted safe SQL candidate. Do not manufacture admission or imply mixed
SQL validation from two positives. Use a separately labeled fixture or a naturally
admitted control from another pinned source if a future SQL accuracy claim needs
