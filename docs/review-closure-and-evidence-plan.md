# Next implementation: closure and reviewer evidence

[AO](experiments/review-cookie-scope-results.md) supports keeping workspace's
qualified state, eight-plus-seven placement and the directory-filter repair.
Neither same-model package is faster in observed active time. The new deciding
problem is that equivalent source mechanisms can become either qualified issues
or unresolved applicability questions, while some short caller citations point at
the wrong nearby routes. Another unchanged grouping/speed experiment will not
resolve either problem.

This is the next bounded implementation plan, not a new live authorization or a
proposal to replace native review. Complete SQL constructions and local API work
stay native initially; relationship investigations can retain workspace state.

Initial prototype: AO's raw `closure-worksheet.md` joins eight cases and 32 original
results with no relabeling or model calls. The subsequent [AP implementation](experiments/review-reviewer-view-results.md)
now makes existing closure state reviewable through the product Markdown/CLI
renderer: shared questions/notes once, claim focus, exact reasons/qualifications
and addressed captured source. Six saved packages preserve all 52 results and
their JSON identities. No schema extension was needed. The evaluator worksheet
remains separate; its manual interpretation is not imported into product output.

## 1. Make existing closure information reviewable

Build an offline comparison/view from current native questions, results,
propositions, conditions, exclusions and latest question-attempt reasons. Start
with AO's shared cookie cases, coupon, requested sensitive fields and generated
roles. Reuse their exact source-bound data and keep evaluator interpretation
separate. Do not change the paid verdicts or automatically convert needs-review
results into issues.

Show four items together:

- The exact selected native question and its source conclusion.
- The model's outstanding or answered question, affected claim IDs and latest
  reason. Show one shared question once with links to its callers.
- Explicit applicability/contract conditions and exclusions, with their origin.
- Any stronger impact or operation question, distinguished from the selected
  mechanism. Source references and uncertainty must remain visible.

The current state already contains much of this information. First inspect the
rendered package and native envelope; add presentation or joins where information
is hidden. Stop schema expansion if existing fields suffice. Avoid a new fact
engine, required progress diary or another generic selected-scope instruction:
the runtime and category guide already contain that instruction.

Use a small contrast matrix before changing model behavior:

| Deciding work | Appropriate closure boundary |
| --- | --- |
| Complete SQL construction/binding and relevant transformations | The injection mechanism can close locally; do not require full operation/caller discovery |
| Authorization or credential effect | Inspect the relevant accepted authority, selector/check and effect; a genuinely missing binding can remain deciding |
| Cookie-authenticated mutation | Separate the established source mechanism from browser/attacker-context conditions; retain conditional findings or precise uncertainty without blanket immunity or deployed-exploit claims |
| Unbounded coupon argument | Numeric enforcement/generation is the selected mechanism; redemption/LLM attack success is an additional impact question unless explicitly selected |
| Sensitive field reaches JSON | Keep local authenticated/self scope; cross-origin JSONP is a further conditional chain |
| Generated sensitive write | Distinguish direct binding proof, explicit ordinary-API inference and an actually unknown write contract |
| External policy fixture with unavailable implementation | Preserve the genuinely unresolved control; do not force a conditional positive just because other cases allow one |

This is rule-specific closure, not a blanket instruction to stop earlier or
classify all source gaps as findings. Use saved safe controls and the external
policy control as offline checks against unsupported dismissals and overclaiming.
Keep model-authored qualifications intact and untruncated. A useful review package
may contain supported mechanisms, scoped negatives and unresolved relationships.

Deliver a reviewable Markdown/CLI projection first. Verify exact coverage,
question-to-claim links, provenance, conditions/exclusions and stale-fact behavior.
Controller-reconstructible presentation must not require another model pass. Do
not claim that a manual evaluator annotation is automatically available in product
output; label any prototype-only interpretation.

correct previously chosen short citations. Existing native and workspace provider
paths serialize packets and new facts separately; a change only to this Markdown
renderer cannot affect either reviewer's source selection.

completes the offline implementation, not model citation/closure validation.

Use the actual AO/AN basket-item and checkout examples. A physically correct
excerpt can still be the wrong caller evidence. Inspect what source was visible
when the model selected those ranges before choosing a fix.

The first implementation candidate is line-addressed source presentation or
selection through existing stable source handles. Keep raw text, physical ranges,
artifact identities, budgets and snapshots authoritative. Presentation metadata
must not alter source bytes, expand lookup scope, invent bindings or turn partial
fragments into complete source. Apply it to actual source windows/results, not
arbitrary prose or quoted instructions. Preserve cache and attribution semantics.

Verify offline that rendered line addresses round-trip to the exact physical
source and that the correct registration can be selected from source actually
shown. Preserve the negative controls: a complete fixed redirect or bound SQL
query must not acquire a new mandatory caller investigation. Distinguish a missing
caller quote from an unsupported underlying mechanism when broader inspected
source supports it.

Only after the view and source presentation are concrete should one fresh small
paired test target citation/closure behavior on the affected cases, with source,
proof expectations and effective allowances frozen. Count any extra presentation
input and actual time. Do not repeat all fifteen claims simply to chase a faster
aggregate; no full-app run, old-budget resumption or reserved follow-up.

## Keep, narrow or stop

Keep API robustness and coherent question sharing independently of a universal
speed win. Continue a presentation change if reviewers can resolve the selected
question and understand its conditions with less reconstruction. Narrow a change
if it hides a qualification, invents certainty, adds procedural work or makes
local closure require an application investigation. A remaining imperfect case
should identify its own correction rather than invalidate useful unrelated work.

Raw source-cache overlap alone is insufficient evidence for another cache layer
or saved model turns. Existing context may already contain a requested fact;
inspect the deciding question and other queries in that turn before proposing
more preloading. The next work should improve the review package the user receives,
not optimize candidate counts or produce another all-or-nothing benchmark gate.
